## Deviations from SPEC.md

- Commit 6 (`feat(checks)`) left two lines over ruff's 110-character limit in `test_warehouse_types.py`, so `uv run ruff check` fails at that commit; fixed in commit 7.

- Contract `data_type` cannot call project macros: dbt 1.12.5 renders schema YAML without them ("'dt_type' is undefined", observed 2026-10-10). Contracts use inline `{{ 'int64' if target.type == 'bigquery' else 'bigint' }}` expressions instead; `test_warehouse_types.py::test_contract_types_mirror_dt_type` asserts every such expression equals the `dt_type` mapping, so `macros/dialect/types.sql` stays the single source of truth.
- `trailing_median` is split into two macros, `trailing_median` (window step in a CTE) and `trailing_median_finish` (exact median from the BigQuery array; identity on DuckDB), because BigQuery cannot take a median over a window frame in one expression.
- Probe planning details beyond SPEC 10/11 (all metadata-driven): models use `fanout_ratio` on their grain and sources use `dup_key_rate`; row-multiplicity probes (`fanout_ratio`, `rowcount_ratio`) are judged inherited when any dataset parent shows a multiplicity anomaly (duplicates, fan-out, row count or overlapping intervals), because join fan-out does not follow column lineage. `recompute_delta` also has an `exact` mode (share of rows that differ) for dates and integer formulas. The S04 time-zone probe on `raw.stage_events` reaches the zone through a `tz_path` join chain in source meta.
- `dbt build` skips models downstream of a failing test, so their checks report `skip`; the ranker treats skipped checks as neither passing nor failing.
- An extra commit between plan commits 9 and 10 freezes the weights and adds the ADRs, so the history shows the weights fixed before the test seeds ran.
- Worker secrets are declared with `secrets.required` in the wrangler config, so `wrangler types` output does not depend on a machine's `.dev.vars` (otherwise `wrangler types --check` would differ between the Mac and CI). `/api/whoami` (any role) was added for the smoke and doctor checks.
- Workflow step results are serialized to JSON strings explicitly (`workflows/steps.ts`), which keeps step outputs visibly serializable and avoids TypeScript's deep `Serializable<T>` instantiation on lineage types. Tests that inspect step results parse the JSON.
- The grounding validator reads a root cause given as a candidate key (`candidate.1`) as that candidate's node, and treats the run and incident ids as known identifiers.
- `setup-prod.sh` loads `.env.prod` through Python-quoted assignments and `eval` (bash 3.2 on macOS does not support `source <(...)`), honours `DATATRUST_ENV_FILE` (used by tests), and treats `wrangler whoami` output text, not its exit code, as the login signal (it exits 0 when not authenticated).
- Project-level IAM (BigQuery Job User for the prober and analyst, Service Account Token Creator for Nitish) is granted by gcloud in `setup-prod.sh` rather than `governance.py`, because it needs the Resource Manager and IAM APIs; dataset-level reader grants are in `governance.py`. `datatrust prod reset --yes` deletes the tables in the four datasets (it never runs unless Nitish asks).
- Extra dialect macros `days_between` and `month_start` (date arithmetic argument order differs between DuckDB and BigQuery).
- Raw stage values are ATS labels rather than canonical codes, so the staging "stage code mapping" that scenario T19 corrupts is a real mapping.
- Builder 2: data masking uses the v1 Data Policy API (SPEC 17 names the v2 client, whose `policy_tag` is output only). A second Access service token `datatrust-operator` (operator and viewer) exists because SPEC 15 gives the only service token the runner role while SPEC 18.4 has the smoke create runs. Fine-Grained Reader goes to the gcloud account rather than `DATATRUST_OPERATOR_EMAIL`. Extra CLI command `datatrust run`.
